MCP · solo el porqué

El token de la API vive en el servidor, no en el agente

Propósito: que la sala se lleve el porqué de MCP que da la clase: aislar las credenciales. No es un tutorial; otros ponentes cubren MCP. (2:00)

MCP tiene muchas razones. La que quiero que se lleven hoy, la de la clase de CMU, es el aislamiento de credenciales.
El agente se autentica con su propia clave. El servidor MCP llama a la API real con otra. El modelo no ve ninguna de las dos.
Es la misma idea que la compuerta: el modelo propone, quien tiene las llaves ejecuta.

Pasos con →: 1 el modelo propone un tool_use; 2 el agente llama al servidor con su clave MCP; 3 el servidor llama a la API con el token real; 4 el resultado vuelve como tool_result.

Fuente: clase de CMU 11-768, lección 2 (diapositivas 44–45, “credential brokering”): el agente usa su propia clave MCP, el servidor llama a la API con otra, y el modelo no ve ninguna. La clase aclara que las claves estáticas son para enseñanza y que en producción se usan JWT u OAuth.

No es un tutorial y no hay demo de MCP en vivo. No afirmes que MCP “resuelve la seguridad”: aísla una clase de credenciales; la autorización de cada llamada sigue siendo tuya. Si preguntan por detalles de MCP, remite a las otras charlas del evento.

Pregunta para llevarse: ¿qué token de tu agente podría estar al alcance del modelo hoy?

Transición: “Ya tenemos las tres roturas. Falta lo que nos dice si funcionan: medir.”
